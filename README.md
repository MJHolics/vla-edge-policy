# VLA Edge Policy — 로봇 위에서 돌아가는 VLA는 무엇을 포기해야 하는가

> 착수 2026-08-18. WSL2 Ubuntu · RTX 4080 SUPER 16GB · LeRobot · `lerobot/smolvla_libero`(450M) ·
> LIBERO-Spatial · ROS2 Jazzy. 상세 측정 서사는 `RESULTS.md`(정정 이력 포함, 1,000줄+), 측정 설계는
> `PLAN.md`, ROS2 브릿지는 `docs/ros2_bridge.md`.
> **한 줄**: LIBERO 성공률은 이미 98%로 포화됐다. 포화되지 않은 축은 **"그 정책이 로봇 제어 주기
> 안에 도는가"**이고, SmolVLA는 RTX 4080에서 20Hz 폐루프(1스텝 50ms)를 지키지 못한다.

---

## 1. 목표·이유 — 왜 했는가

VLA(Vision-Language-Action)가 2026년 embodied AI의 중심축이지만, 표준 벤치마크 LIBERO의 평균
성공률은 16개월 만에 75%→98%로 사실상 포화됐다. 여기서 +0.5%p를 다투는 건 대형 연구실의
일이고, 포트폴리오로도 "돌려봤다"와 구분되지 않는다. **포화되지 않은 축**은 따로 있다 — VLA
추론은 로봇 안/옆 하드웨어에서 제어 주기 안에, 지연 상한이 보장된 채 돌아야 한다. 성공률
98%짜리 정책도 5Hz로만 돌면 로봇 위에서는 못 쓴다. 그래서 이 프로젝트가 재는 건 **정확도가
아니라 "제어 주기 제약 아래에서의 정확도"**다.

## 2. 상품성 — 누가 왜 쓰나

로봇/제조 자동화 회사에서 "이 정책을 우리 컨트롤러에 올릴 수 있나"에 답해야 하는 온보드 추론
담당이 대상이다. 모델 선택을 성공률 단일 지표가 아니라 **(성공률, 제어 주기, 메모리) 삼중
제약**으로 바꾸고, "어떤 압축을 어디까지 하면 몇 Hz가 나오고 성공률을 얼마나 잃는가"를 실측
표로 준다.

## 3. 아키텍처·측정 채용 근거

- **LeRobot(HuggingFace)**: VLA·모방학습 정책이 한 인터페이스로 모여 있어 정책 간 공정 비교가
  가능한 사실상의 표준.
- **LIBERO-Spatial**: VLA 평가의 사실상 표준이라 공개 수치와 직접 비교 가능. 자체 환경을 만들면
  비교 대상이 사라진다.
- **SmolVLA-450M**: 소비자 GPU 대상 설계, RTX 4080 SUPER(16GB)에서 bf16 파인튜닝 가능이 문헌으로
  확인된 모델.
- **제어 주기 예산은 문헌값이 아니라 이 임베디먼트의 실제 설정값(`LiberoEnv.fps`)으로 확정** —
  20Hz(1스텝 50ms). 문헌의 "30~100Hz"를 그대로 쓰지 않고 소스를 확인해 정정한 결정이다.
- **성공률은 sim 롤아웃, 지연은 정책 단독(env 제외)으로 분리 측정**: env(시뮬레이터) 종단 상한이
  8~9Hz로 정책보다 느려서, 섞어 재면 결론 전체가 오염된다는 걸 먼저 확인하고 설계를 나눴다.

## 4. 성능 비교(실측)

| 축 | 실측 | 조건 |
|---|---|---|
| 정책 단독 지연(낮은 모드) | **49~60ms** | num_steps=1, 50ms 예산에 근접 |
| 정책 단독 지연(높은 모드, 실제 관측) | **119~153ms(2.4~3.1배 초과)** | 같은 조건, 이봉 분포 |
| 디노이징 10→1 축소 | 지연 3.43~4.19배 단축 | 4회 재측정 범위(단일값 아님) |
| 위 축소의 대가(표준 프로토콜 n=500) | 성공률 **57.4%→52.2%(−5.2%p)** | McNemar 정확검정 **p=0.018**, 유의 |
| ROS2 서비스 브릿지 오버헤드 | 왕복 지연의 **0.5% 미만**(1.52ms) | rclpy 서비스, 20Hz 타이머 폐루프 실제 달성 **2.87Hz** |
| 이봉 지연의 원인 | GPU 클럭 아님(저/고지연 버킷 클럭차 105MHz, 무관) → **CUDA 커널 제출 경로 시간과 상관계수 r=0.989** | Nsight Systems, NVTX 레인지 단위 집계 |
| MuJoCo 물리 도메인 랜덤화(마찰·질량) | 성공률 변화 **유의하지 않음**(McNemar p=0.36) | n=150/조건, 몽키패치 직접 조작 |
| MuJoCo 시각(색상) 도메인 랜덤화 | 성공률 **+13.3%p, 유의함**(p=0.00119) — **원인은 미규명, 확장 안 함** | rgba 0.6~1.4배 |

**읽는 법**: "디노이징을 줄이면 공짜로 빨라진다"는 n=50 초기 결론이었으나, 표본을 10배로 늘리고
짝지음 검정을 쓰자 **대가가 드러났다(폐기 기록 §6)**. 이봉 지연은 처음 "드리프트"라 불렀지만
원시 분포를 열어보니 두 개의 고정된 봉우리였고, 그 원인을 GPU 클럭 → 커널 제출 경로까지 3단계
후속 실험으로 좁혔다.

## 5. 교체·의사결정 기록

| 결정 | 버린 안 | 택한 안 | 근거 |
|---|---|---|---|
| 지연 평가의 "공짜" 결론 | n=50, Wilson 구간 겹침만 확인 | n=500 표준 프로토콜 + McNemar 짝지음 검정 | 작은 표본은 "차이 없음"이 아니라 "못 잡는다"였다 — 실제로 5.2%p 대가가 있었다 |
| 이봉 지연 원인 1순위 가설 | GPU 클럭 램핑(추정) | 직접 측정(`nvidia-smi -q`)으로 기각, Nsight Systems로 커널 제출 경로 확인 | 저/고지연 버킷 클럭차 105MHz로 작음, 클럭 고정 구간에서도 지연이 흔들림 |
| A/B 교차 설계 | ABAB(카메라 유/무) | ABBA로 재설계 | ABAB는 뒤쪽 조건이 항상 시간 드리프트를 더 받아 카메라 효과와 분리 안 됨 |
| 제어 주기 예산 값 | 문헌 인용(30~100Hz) | `LiberoEnv.fps` 소스 확인(20Hz) | 문헌값을 그대로 쓰면 이 임베디먼트와 무관한 예산이 된다 |
| 소규모 평가(n=50) 사용 여부 | 계속 60~64%로 인용 | 폐기, 57.4%로 대체 | init_state_id=episode_index라 앞 5개만 뽑는 비무작위 표본이었음(+8.6%p 낙관 편향) |

## 6. 에러 대처 기록

1. **`Feature mismatch` 크래시 → 손잡이 두 개(`rename_map`·`empty_cameras=1`)를 동시에 돌려 해결한
   줄 알았지만, 실제로 필요했던 건 하나뿐이었다.** `empty_cameras=1`은 학습에 없던 카메라를
   −1 패딩으로 밀어 넣는 것이었는데, A/B(50에피소드)로 재보니 효과가 무해(+4.0%p, 구간 겹침)했고
   원래 실패 원인(task 4·5)에는 미동도 없었다. **에러가 사라진 게 어느 손잡이가 고쳤는지의
   증거가 아니라는 교훈.**
2. **성공률 57.4%가 공개 수치(90%대)와 크게 벌어져 원인을 추적**했다. 1순위 가설(카메라 3대
   학습 vs 2대 평가)은 데이터셋을 직접 열어 기각(학습 자체가 2대), state 차원 불일치(6 vs 8)도
   런타임 값을 학습 정규화 통계와 대조해 기각(둘 다 원인 아님) — 격차는 두 결함이 아니라 **평가
   자체의 낙관 편향(비무작위 소표본)**이었다.
3. **`nvidia-smi -lgc`(GPU 클럭 고정)가 이 WSL2 환경에서 근본적으로 불가능**(`Unknown Error`,
   NVML 호출이 패스스루 안 됨). 대신 클럭·전력을 관측만 하는 프로브로 우회해 클럭 가설을
   기각까지는 할 수 있었다.
4. **nsys(Nsight Systems) 트레이싱 자체가 타이밍을 크게 흔든다**(클럭이 900MHz대로 떨어짐) —
   트레이싱 중 절대 지연값은 인용하지 않고, API 호출 분포 모양(중앙값 vs 꼬리)만 근거로 썼다.
5. **Windows 호스트의 백그라운드 GPU 경합**(Riot Vanguard·Overwolf 등 18개 프로세스가 GPU
   컨텍스트를 쥐고 있었음)을 종료해 평균 지연 29% 개선을 확인했지만, **상대적 흔들림(CV)은
   그대로**였다 — 부분 원인이지 유일한 원인은 아니라고 정직하게 남겼다.

## 7. 개발 순서

1. 목표를 "성공률"이 아니라 "제어 주기 제약 하 성공률"로 먼저 재정의(PLAN.md §①)하고, 측정
   설계(지표 3축·프레임워크·벤치마크 선택)를 **코드 작성 전에** 확정.
2. env(시뮬레이터) 비용을 정책보다 먼저 측정해 8~9Hz 상한을 확인 → 성공률/지연 측정을 분리하는
   설계 결정.
3. 디노이징 스텝 스윕(n=50) → "공짜로 빠르다"는 잠정 결론 → 이봉 분포 발견 → ABAB 실패 →
   ABBA 재설계 → GPU 클럭 가설 검증(기각) → Nsight Systems 커널 제출 경로 분석(r=0.989)까지
   4단계 후속 조사.
4. 표준 프로토콜(n=500, 짝지음 McNemar)로 재측정해 "공짜" 결론을 폐기하고 5.2%p 대가를 확정.
5. ROS2 서비스 브릿지(rclpy 노드·타이머 폐루프)로 정책을 감싸 미들웨어 오버헤드(<0.5%)를 별도
   측정(2026-09-02, `docs/ros2_bridge.md`).
6. MuJoCo 물리·시각 도메인 랜덤화를 몽키패치로 직접 조작해 짝지음 비교(2026-09-03~10) — 물리는
   유의하지 않음, 시각(색상)은 유의하지만 원인은 미규명으로 정직하게 남김.

## 범위와 한계 (정직하게)

- 전부 **RTX 4080 SUPER(WSL2) 단일 GPU** 실측이다. 실제 온보드 컴퓨터(Jetson 등)의 절대 Hz가
  아니라 **구성 간 상대 비교와 압축의 대가**가 결론이다.
- 이봉 지연의 정확한 원인(WSL2 GPU-PV 채널의 어느 부분이 혼잡한지)은 **미확정**이다 — 베어메탈
  Linux 비교 없이는 이 이상 못 좁힌다고 판단하고 멈췄다.
- 시각 도메인 랜덤화의 성공률 개선(+13.3%p, p=0.00119)은 통계적으로는 분명하지만 **왜** 그런지는
  모델 내부 조사가 필요한 별도 질문으로 남겼다 — "시각 강건성이 확인됐다"로 확장하지 않는다.
- ROS2 브릿지는 같은 머신의 loopback 통신까지가 근거다. 실물 로봇·네트워크 분리 환경은 다루지
  않았다.
